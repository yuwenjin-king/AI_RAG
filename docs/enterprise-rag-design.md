## 1. 概述

### 1.1 项目背景

随着企业内部知识、专业领域文档、代码资产的持续增长，传统关键词检索与单纯依赖大模型内生知识问答已无法满足准确性与时效性要求。检索增强生成（RAG, Retrieval-Augmented Generation）通过"检索外部知识 + 大模型生成"的方式，能够显著降低幻觉率、提升答案的可追溯性，是当前企业级智能问答、知识管理、代码辅助等场景的核心技术路线。

### 1.2 设计目标

本系统定位为**多租户、多场景通用的企业级 RAG 检索平台**，而非绑定单一业务的问答系统，核心目标包括：

- **通用性**：以插件化方式支持知识库问答、专业领域问答、代码检索等多种场景，通过配置而非重新开发适配新场景
- **规模化**：支持百万级文档、千万级 Chunk 的索引与检索，支持中高并发（目标 QPS 数百级，可平滑扩展至千级）
- **高准确率**：通过混合检索、重排序、引用溯源等机制保证答案质量与可解释性，**溯源需精确到原文档的具体页面与区域，而非仅到文档级**
- **高可用**：核心链路可用性 ≥ 99.9%，具备容灾与降级能力
- **可运营**：具备完整的数据接入、效果评估、监控告警、成本管控能力
- **安全合规**：满足多租户数据隔离、权限控制、审计留痕要求
- **完整产品闭环**：不仅提供后端检索/生成能力，同时给出前端交互产品形态设计（React + FastAPI），实现从数据接入到用户交互的端到端方案

### 1.3 非目标（Out of Scope）

- 不包含底层大模型的预训练/微调（本设计假定通过 API 或自建推理服务调用 LLM）
- 不包含具体 UI 视觉稿/像素级设计规范，仅给出产品形态、页面结构与前后端接口设计

## 3. 总体架构

系统采用**分层解耦架构**，自下而上分为：数据接入层、知识处理层（含 PDF 视觉解析）、存储与索引层、检索编排层、生成与应用层、前端交互层、平台治理层。

│                        平台治理层（横向贯穿）                       │
│   租户与权限管理 │ 配置中心 │ 监控告警 │ 评估与标注 │ 审计日志           │
└─────────────────────────────────────────────────────────────────┘

┌──────────────────┐
│   前端交互层        │   React + TS：对话问答 / 知识库管理 / 原文档预览高亮
│  (React SPA)      │
└─────────┬─────────┘
          │ HTTPS / SSE
┌─────────▼─────────┐
│  应用网关层         │   FastAPI (BFF)：鉴权、请求编排、流式转发
└─────────┬─────────┘
          │
┌───────────────┐   ┌────────────────────┐   ┌───────────────┐   ┌───────────────┐
│  数据接入层     │→ │  知识处理层           │→ │ 存储与索引层   │←→│ 检索编排层     │

                     └────────────────────┘   └───────────────┘  └───────┬───────┘

                                                          │ - 引用溯源与后处理(page+bbox)   │
                                                          └────────────────────────────────┘
```

### 3.1 架构设计原则

1. **检索与生成解耦**：检索服务可独立对外提供 API（供其他系统复用），不强绑定生成环节
2. **场景配置化**：通过"知识库 + 检索策略 + Prompt 模板 + 权限规则"四要素组合，实现新场景秒级接入
3. **多路召回 + 统一精排**：不同检索方式并行召回，通过统一 Reranker 融合排序，避免单一检索方式的召回盲区
4. **异步化数据处理**：文档解析、版面检测、分块、Embedding 计算通过消息队列异步化，避免阻塞在线链路
5. **无状态服务 + 有状态存储分离**：检索、生成、BFF 服务无状态，便于水平扩展；状态收敛到向量库、数据库、缓存
6. **溯源信息全链路透传**：从解析阶段产生的页码/坐标信息，需随 Chunk 元数据贯穿存储、检索、生成、前端展示全链路，不能丢失

## 4. 详细模块设计

### 4.1 数据接入层

**职责**：对接多种数据源，完成数据的拉取、变更感知与初步校验。

- **连接器（Connector）框架**：抽象统一的 Connector 接口，内置文件系统、对象存储（OSS/S3）、数据库（MySQL/PostgreSQL）、Wiki 类系统（Confluence/飞书文档）、API 数据源等连接器；新数据源通过实现接口插件化接入
- **增量同步机制**：
  - 支持 CDC（变更数据捕获）用于数据库类数据源
  - 支持基于 hash/时间戳的差量比对，用于文件类数据源
  - 变更事件统一发布至消息队列（Kafka），驱动下游异步处理
- **数据校验与清洗**：格式校验、敏感信息脱敏（PII 识别）、重复文档检测（SimHash/MinHash）

### 4.2 知识处理层

**职责**：将原始文档转化为可检索的标准化知识单元（Chunk）及其向量表示，并保留精确溯源信息。

**4.2.1 文档解析总体路由**

按文件类型路由至专用解析器：Office 文档、HTML、Markdown、代码文件（AST 级解析）走结构化解析；**PDF 因排版复杂性单独设计解析方案（见 4.2.2）**。解析结果统一为标准中间表示（结构化 JSON：标题层级、段落、表格、图片描述、代码块、页码、坐标等）。

**4.2.2 PDF 解析方案：是否引入视觉模型（YOLO 类版面检测）**

这是保证"精确追溯到原文件"这一目标能否实现的关键决策点，采用**分级处理策略**，而非对所有 PDF 统一使用重量级视觉模型：

**（1）为什么需要视觉版面检测**

纯文本抽取工具（如 PyMuPDF、pdfplumber）直接读取 PDF 文本层，存在以下问题：

- 多栏排版、页眉页脚、脚注混排时，文本抽取顺序容易错乱，导致语义被割裂
- 表格结构容易被打散成无序文本，丢失行列关系
- 扫描件（图片型 PDF）没有文本层，必须依赖 OCR
- **最关键的问题**：纯文本抽取通常只能定位到"字符流中的位置"，难以直接映射回 PDF 页面上的**精确像素坐标（bounding box）**，导致前端无法在原文档上画出高亮框，只能做到"跳转到某一页"这种粗粒度溯源

**（2）引入版面检测模型的方案**

- **技术路线**：PDF 按页转图片 → 版面检测模型识别页面中的区域块（标题、正文、表格、图片、页眉页脚等）并输出类别 + bbox 坐标 → 按区域类型分流处理（表格走表格结构识别、正文走文本抽取或 OCR、图片走图片理解生成描述）→ 每个最终 Chunk 携带 `{doc_id, page_no, bbox: [x0,y0,x1,y1]}` 溯源元数据
- **模型选型方向**：
  - YOLO 系列的版面检测思路（如社区中的 DocLayout-YOLO 等文档版面检测方案）：基于目标检测框架微调，专门识别文档版面元素，速度快、易部署，适合大批量离线处理
  - 也可选用 PaddleOCR 系（PP-Structure）、LayoutLM 系列等文档理解模型，各有精度/速度权衡，需结合实际数据做选型评测
  - 表格区域建议接专用表格结构识别模型，效果通常优于让版面检测模型直接输出表格内容
- **是否必须用 YOLO**：不是唯一选项，核心诉求是"获得可靠的区域级 bbox"。若 PDF 为原生文本型（非扫描件）且排版规整，可先尝试通过 PDF 自身的文本层坐标信息（多数 PDF 解析库能返回每个文本块的坐标）直接获取 bbox，无需额外视觉模型；仅当文本层缺失（扫描件）或版式复杂（多栏、大量表格）导致直接抽取效果差时，才触发视觉版面检测 pipeline。

**（3）分级处理策略（成本与效果的平衡）**

| PDF 类型 | 处理方式 | 说明 |
|---|---|---|
| 原生文本型 + 规整排版 | 文本层直接抽取 + 坐标信息获取 bbox | 成本低、速度快，覆盖大部分场景 |
| 原生文本型 + 复杂排版（多栏/密集表格） | 触发版面检测模型 + 分区域处理 | 提升解析准确率，避免语义割裂 |
| 扫描件/图片型 PDF | 版面检测 + OCR（区域级识别） | 必须走视觉路线，否则无文本可用 |

判定逻辑可在解析入口做轻量启发式检测（是否存在文本层、文本层覆盖率、版式复杂度评分），自动路由到对应处理分支，而非人工指定。

**（4）工程实现要点**

- 视觉解析（版面检测 + OCR）计算成本高于纯文本抽取，建议部署为**独立的 GPU 推理服务/任务池**，通过消息队列异步调度，与主数据处理链路解耦，避免影响其他文档类型的处理时效
- 每个 Chunk 的元数据中固化保存 `page_no` 与 `bbox`（归一化坐标，兼容不同渲染分辨率），随 Chunk 一同写入向量库/元数据库，供后续检索结果与前端展示复用
- 原始 PDF 文件本身需保留在对象存储中（而非仅存解析后文本），前端预览与高亮定位依赖对原文件的重新渲染

**4.2.3 分块（Chunking）策略**

| 策略 | 适用场景 | 说明 |
|---|---|---|
| 固定长度 + 重叠 | 通用兜底 | 简单高效，重叠窗口降低边界信息丢失 |
| 语义分块 | 知识库问答 | 基于句子/段落语义相似度动态切分，保持语义完整性 |
| 结构感知分块 | 结构化文档（含标题/表格） | 按标题层级、表格边界切分，保留层级元数据 |
| 代码感知分块 | 代码检索场景 | 按函数/类/模块级别切分，保留调用关系 |
| 版面区域分块 | PDF（视觉解析路线） | 直接以版面检测输出的区域块为基础单元，天然携带 bbox |
| 父子分块（Small-to-Big） | 需要精确定位又需上下文场景 | 检索用小 Chunk，生成时回溯扩展至父级大 Chunk，兼顾召回精度与生成上下文完整性 |

**4.2.4 Embedding 与元数据抽取**

- 向量化：支持多 Embedding 模型可插拔（区分中文/英文/代码/多语言场景），批量异步计算，结果写入向量库
- 元数据抽取：文档标题、来源、创建时间、权限标签、业务标签、**页码与 bbox（PDF 场景）**
- 摘要/关键词预生成：用于关键词检索路与结果展示

### 4.3 存储与索引层

采用**多存储引擎组合**，各司其职：

| 存储类型 | 选型方向 | 用途 |
|---|---|---|
| 向量数据库 | Milvus / Qdrant / 云厂商向量检索服务 | 稠密向量近似最近邻检索（ANN） |
| 倒排索引 | Elasticsearch / OpenSearch | 关键词/BM25 检索、结构化过滤 |
| 元数据库 | PostgreSQL | 文档元数据、权限、租户配置、Chunk 溯源坐标等强一致数据 |
| 图数据库（可选） | Neo4j / 云图数据库 | 知识图谱场景，实体关系检索（GraphRAG） |
| 对象存储 | OSS/S3 | 原始文档、解析产物、页面渲染缓存图 |
| 缓存 | Redis | 查询结果缓存、热点 Embedding 缓存、会话状态、页面渲染图缓存 |

**关键设计点**：

- **索引分片与租户隔离**：按租户 + 知识库维度进行 Collection/Index 级隔离，避免"noisy neighbor"问题；大租户可独立分片
- **多级索引**：向量索引采用 HNSW/IVF 等 ANN 算法，在召回率与延迟间权衡；支持标量字段过滤（Pre-filter）实现权限与业务过滤前置
- **冷热分层**：低频访问的历史文档索引可降级至低成本存储层，按需加载
- **溯源坐标存储**：`page_no`、`bbox` 作为 Chunk 元数据的标准字段，随向量库/元数据库统一维护，检索结果需完整透传该字段

### 4.4 检索编排层（Retrieval Orchestration）

采用 **"查询理解 → 多路召回 → 融合精排 → 上下文构建"** 四段式流水线。

**4.4.1 查询理解**

- 查询改写：结合多轮对话历史，将指代消解、省略补全后的完整查询用于检索（可用轻量 LLM 完成）
- 查询扩展：同义词/领域术语扩展，缓解词汇不匹配问题
- 意图与路由：判断查询应路由至哪个/哪些知识库、是否需要结构化查询（如数据库 Text2SQL）而非纯文本检索

**4.4.2 多路召回**

- **向量检索**：语义相似度召回，解决同义改写、跨语言等场景
- **关键词检索（BM25）**：解决精确术语、专有名词、编号类查询的召回短板
- **结构化过滤**：基于元数据（时间、部门、权限标签）的硬过滤，与前两路结合
- 各路召回 Top-N（如 N=50~100），进入融合阶段

**4.4.3 融合与精排（Rerank）**

- 初步融合：RRF（Reciprocal Rank Fusion）等算法融合多路召回结果，去重合并
- 精排：使用 Cross-Encoder 类重排序模型对候选集重新打分，输出最终 Top-K（如 K=5~10）
- 可选：多样性控制（MMR）避免结果高度冗余

**4.4.4 上下文构建**

- 父子分块回溯：将精排后的小 Chunk 扩展为包含上下文的完整片段
- 上下文压缩：结合 Token 预算，对长上下文做摘要/裁剪，避免超出 LLM 上下文窗口或稀释关键信息
- 引用标注：为每个上下文片段保留 `doc_id / page_no / bbox` 等来源信息，供生成阶段与前端展示引用

### 4.5 生成与应用层

- **Prompt 编排中心**：按场景管理 Prompt 模板（系统提示、few-shot 示例、输出格式约束），支持版本管理与灰度
- **LLM 网关**：
  - 多模型路由：按场景/成本/延迟要求路由至不同模型
  - 失败降级：主模型不可用时自动切换备用模型/服务商
  - 限流与配额：按租户/场景配置调用配额，防止成本失控
- **后处理**：引用来源标注（含 page_no/bbox）、答案格式化、敏感内容过滤、"未检索到相关信息"的兜底话术
- **场景化 Agent（可选扩展）**：对需要多步推理、工具调用的复杂场景，在检索基础上叠加 Agent 编排层

## 5. 前端交互与产品形态设计（React + FastAPI）

### 5.1 产品形态定位

以**对话式检索问答**为核心交互形态，辅以知识库管理后台与运营配置台，整体分为三类用户视角：

- **终端用户**：使用对话问答界面提问，查看答案与可追溯的原文引用
- **知识库管理员**：负责数据源接入、文档上传、索引状态监控
- **平台运营/场景负责人**：负责场景配置（Prompt、检索策略、权限规则）、效果监控

### 5.2 前端页面结构（React）

| 模块 | 功能说明 |
|---|---|
| 对话问答主界面 | 多轮对话、流式打字机效果输出（消费 SSE）、答案下方展示引用来源卡片（文档名+页码+片段预览缩略图） |
| 原文档预览与高亮定位 | 点击引用卡片后，弹出/侧边栏渲染原 PDF 对应页面，并根据 bbox 坐标在页面上绘制高亮框，精确定位到引用区域 |
| 知识库管理台 | 数据源/连接器配置、文档上传（含进度与解析状态展示）、索引状态查看（解析中/已索引/失败重试） |
| 场景与策略配置台 | Prompt 模板管理、检索参数（Top-K、是否启用 Rerank、召回路数）配置、模型路由规则配置 |
| 反馈与标注 | 答案点赞/点踩、标注入口，用于效果评估闭环 |
| 监控看板 | 调用量、延迟、成本、召回率等指标可视化（可对接现有 BI/监控工具，不必自建） |

### 5.3 关键交互设计要点

- **流式响应**：生成阶段通过 SSE（Server-Sent Events）向前端逐 token 推送，前端做打字机效果渲染，降低用户感知延迟
- **引用溯源交互**：这是本系统区别于普通问答产品的核心体验——引用不是简单的"文档名+链接"，而是可点击定位到**具体页面 + 具体区域高亮**的精确溯源，依赖 4.2.2 节的 PDF 视觉解析能力产出的 `page_no/bbox` 数据
- **加载态与降级提示**：检索无结果、模型降级、超时等情况需要有明确、友好的前端状态提示，而非静默失败

### 5.4 前端技术栈

- **框架**：React + TypeScript
- **状态管理**：Zustand / Redux Toolkit（会话状态、流式消息缓冲）
- **PDF 渲染与高亮**：PDF.js（按 `page_no` 渲染指定页，按归一化 `bbox` 坐标换算为实际像素位置绘制高亮层）
- **组件库**：Ant Design 或自建轻量设计系统，保证管理台类页面（表格、表单密集）开发效率
- **流式数据处理**：EventSource / fetch + ReadableStream 处理 SSE

### 5.5 后端技术栈：FastAPI 作为 BFF（Backend for Frontend）

FastAPI 服务在整体架构中承担"应用网关层"角色，是前端与后端各服务（检索编排层、生成与应用层、知识处理层）之间的编排枢纽，而非直接承载重计算逻辑：

- **职责**：
  - 用户鉴权与会话管理（JWT + RBAC，通过依赖注入做接口级权限校验）
  - 请求编排：接收前端请求 → 调用检索编排层 API 获取上下文 → 调用 LLM 网关生成答案 → 流式转发给前端
  - SSE/WebSocket 流式转发：利用 FastAPI 原生异步（async/await）能力，天然适合高并发 IO 密集型的流式场景
  - 文档上传：生成对象存储预签名 URL，前端直传，减轻后端带宽压力；上传完成后触发数据处理流水线
  - 溯源查询接口：根据 chunk_id 返回渲染定位所需的 `page_no + bbox`

- **核心 API 设计（示例）**：

```
POST   /api/v1/chat                     # 对话问答，SSE 流式返回 token 与引用列表
GET    /api/v1/conversations/{id}       # 获取历史会话
POST   /api/v1/documents/upload-url     # 获取文档上传预签名 URL
GET    /api/v1/documents                # 文档列表与索引状态
GET    /api/v1/documents/{doc_id}/locate?chunk_id=xxx   # 返回 page_no + bbox 溯源定位信息
POST   /api/v1/feedback                 # 提交点赞/点踩/标注
GET    /api/v1/admin/scenes/{scene_id}/config           # 场景配置读取
PUT    /api/v1/admin/scenes/{scene_id}/config           # 场景配置更新
```

- **部署形态**：FastAPI 服务本身无状态，与检索编排层、生成层一样纳入 Kubernetes 部署，独立扩缩容；作为对外唯一入口，前置于 API 网关之后，统一处理跨域、限流、日志采集

### 5.6 前后端数据流示例（一次问答请求）

```
React 前端                FastAPI(BFF)            检索编排层        生成与应用层
    │  POST /chat               │                     │                  │
    ├──────────────────────────►│                     │                  │
    │                           │  查询检索接口         │                  │

## 6. 多租户与权限设计

作为多场景通用平台，多租户是核心能力而非附加特性：

- **隔离粒度**：租户级（Tenant）→ 知识库级（KnowledgeBase）→ 文档级（Document）三级隔离
- **索引隔离策略**：
  - 大租户/高安全等级：独立 Collection/Index（物理隔离）
  - 中小租户：共享 Collection + 租户 ID 字段过滤（逻辑隔离），降低资源开销
- **权限过滤**：检索时将用户可见的文档/标签范围作为**前置过滤条件**注入检索请求，而非检索后过滤，避免权限泄露且提升效率
- **配置中心**：每个场景/租户的检索策略、Prompt 模板、模型路由规则均通过配置中心管理，支持灰度发布，前端"场景与策略配置台"即对应此模块的可视化入口

## 7. 高可用与弹性设计

| 环节 | 高可用策略 |
|---|---|
| BFF（FastAPI） | 无状态部署，多可用区，负载均衡 + HPA 自动扩缩容 |
| 检索服务 | 无状态部署，多可用区（AZ）部署，负载均衡 + 自动扩缩容 |
| 向量数据库 | 集群化部署（副本 + 分片），跨 AZ 容灾 |
| PDF 视觉解析服务 | 独立 GPU 资源池，异步队列调度，与在线链路解耦，故障不影响检索问答主链路 |
| 消息队列 | Kafka 多副本，保证数据处理管道不丢消息 |
| LLM 调用 | 多模型/多供应商降级链路，超时熔断（Circuit Breaker） |
| 缓存 | Redis 集群模式，缓存穿透/雪崩防护 |
| 全链路 | 关键路径设置超时与降级预案（如向量检索超时则仅用关键词检索兜底；视觉解析超时则先用纯文本抽取兜底再异步补齐 bbox） |

**弹性伸缩**：基于 QPS/延迟/队列积压等指标配置自动扩缩容策略；数据处理管道（解析、版面检测、Embedding）与在线检索/BFF 服务资源池分离，避免批量任务抢占在线资源。

## 8. 安全与合规

- **传输安全**：全链路 TLS 加密，前端与 FastAPI 间使用 HTTPS
- **存储安全**：静态数据加密（向量库、对象存储、数据库均启用加密），原始 PDF 文件同样加密存储
- **访问控制**：基于 RBAC 的 API 访问控制，FastAPI 层做接口级鉴权，服务间调用采用 mTLS/内部 Token
- **数据脱敏**：接入阶段识别并脱敏 PII 信息（视业务合规要求可选）
- **审计**：记录查询日志、检索命中来源、生成内容、原文档访问日志，满足审计追溯需求
- **合规**：根据部署地区与行业满足对应数据合规要求，公有云部署需评估云厂商的合规资质

## 9. 效果评估与运营体系

- **离线评估集**：按场景构建 Query-标准答案/标准引用 评估集，定期回归测试
- **核心评估指标**：
  - 检索层：Recall@K、MRR、NDCG
  - **PDF 溯源准确率**：抽样评估 bbox 定位是否命中正确区域，作为视觉解析质量的专项指标
  - 生成层：答案准确率、忠实度（Faithfulness）、引用准确率
  - 体验层：端到端延迟、拒答率
- **在线反馈闭环**：用户点赞/点踩、人工标注平台，反馈数据用于优化分块策略、检索参数、Prompt
- **A/B 测试框架**：支持检索策略、模型、Prompt 版本的灰度对比实验
- **监控告警**：检索延迟、召回率异常、视觉解析失败率、LLM 调用失败率、成本超阈值等指标接入统一监控（Prometheus + Grafana）

## 11. 部署架构（公有云）

- **计算层**：Kubernetes 集群，前端静态资源（CDN分发）、FastAPI(BFF)、检索服务、生成网关、数据处理 Worker、视觉解析 GPU Worker 分别独立部署，按负载特征独立扩缩容
- **多可用区部署**：核心存储（向量库、ES、PG）与无状态服务均跨至少 2 个可用区
- **网络**：通过 API 网关统一对外暴露 FastAPI 服务，内部服务间通过服务网格（可选）或轻量 RPC 通信
- **CI/CD**：前后端镜像构建、灰度发布、自动化回归测试（含离线评估集回归）纳入发布流水线
- **成本优化**：
  - 数据处理与视觉解析类任务使用 Spot/抢占式 GPU 实例降低成本
  - 视觉解析按分级策略仅对必要文档触发，避免全量滥用
  - 向量索引冷热分层，PDF 页面渲染图做缓存复用
  - 结合缓存与模型路由降低 LLM 调用成本

## 13. 主要风险与应对

| 风险 | 应对措施 |
|---|---|
| 分块策略不当导致召回率低 | 建立离线评估集，支持多策略并行 A/B，按场景调优 |
| 多租户资源争抢 | 分级隔离策略 + 资源配额 + 监控告警 |
| LLM 服务不稳定/成本波动 | 多模型路由与降级、调用配额管理、缓存复用 |
| 权限泄露 | 前置过滤而非后置过滤，权限规则纳入检索请求强制校验，定期安全审计 |
| PDF 视觉解析成本过高 | 分级处理策略（仅复杂/扫描件触发），独立 GPU 资源池按需扩缩容 |
| bbox 定位不准影响体验 | 建立溯源准确率专项评估指标，人工抽样校验，模型选型前充分评测 |
| 新场景接入成本高 | 坚持配置化架构原则，避免场景强耦合到代码逻辑 |
| 数据规模增长后索引性能退化 | 提前规划分片策略与冷热分层，压测验证扩展性 |

## 14. 总结

本设计以"检索与生成解耦、场景配置化、多路召回+统一精排、多租户隔离"为后端核心架构原则，并在此基础上补充了两个关键能力：

1. **完整前端产品闭环**：以 React 构建对话式问答与管理台前端，FastAPI 作为 BFF 承担鉴权、请求编排与流式转发职责，形成从数据接入到用户交互的端到端方案；
2. **PDF 精确溯源方案**：通过按需引入版面检测视觉模型（YOLO 类方案为代表），获取区域级 bbox 坐标，结合 PDF.js 实现"点击引用即可定位原文档具体区域高亮"的体验，同时通过分级处理策略控制视觉解析带来的额外成本。

建议按照第 12 节路线图分阶段实施，先以单场景 MVP（含基础前端与简化版溯源）验证核心链路，再逐步增强溯源精度、平台化与规模化，并将效果评估体系（含溯源准确率）作为长期基础设施同步建设。
